## Repair 6 in one page

Review #6 (independent Codex session, `reviews/bootstrap-v4-kernel-codex-review-6.md`) replayed **N16**: an opaque byte copy of the dedicated Keychain file taken at anchor sequence 0 still opened, after the anchor had advanced to 1, with the *unchanged* login-Keychain password item, because the password never changed across advances. Restoring that copy with its matching earlier database restored a revoked decision. The R-K2 statement "rollback needs a whole login-Keychain restore" was therefore wrong. Review #6 and its reproduction evidence are preserved unchanged.

**Repair (direction chosen by Thomas: rotate the password on every advance).** After every `Set` with an expectation and every `Revert`, the dedicated file is re-keyed to a fresh random 32-byte password (`SecKeychainChangePassword`), after the anchor state is written and read back. A copy taken at any earlier step carries an earlier password and no longer opens with the current login-Keychain item; it reads as **corrupt** and only the governed re-anchor recovers. A freshly created file is not re-keyed (fresh password, no earlier copy). Crash safety: the new password is written to a `:pending` login-Keychain item first, then the file is re-keyed, then the current item is updated, then the pending item is removed; `openWithRecovery` finishes an interrupted re-key from either side and discards stale or malformed pending items. If the re-key fails, the advance is written back and the `Set` is refused as *unavailable*, so the anchor is exactly where it was; if the write-back also fails the anchor is one step ahead of the store (the stranded fail-closed state), and the error says so. Design: `repair-6-evidence/design/rekey-lifecycle.md` (amends the preserved Repair 5 design §7.1, which is unchanged).

**The new dependency, stated no more strongly than the evidence.** `SecKeychainChangePassword` is exported by Security.framework but is **not in its public headers and not documented as stable**; the whole `SecKeychain*` family is deprecated. It is resolved at run time with `dlsym`, so a macOS without it makes every re-key, and therefore every anchor advance, fail closed as *unavailable* while reads keep working (modelled by naming a symbol that does not exist; the real one cannot be removed from a running system). It was **measured only on macOS 26.6.2 (25G83), arm64, Go 1.27.1**, where the symbol resolves and the re-key succeeds with user interaction disabled for the call. No other macOS version was tested; nothing here is a portability claim.

**Residual, retained and corrected (R-K2).** A coordinated restore of the database, the dedicated Keychain file, **and the corresponding earlier login-Keychain password state** can still restore a consistent earlier state. Closing that rollback domain requires a monotonic trust anchor outside the rollback set, which D1 excluded. The re-key moved the replay target from the dedicated file alone to the login Keychain's password item as well; it did not remove the class, and the design was not silently expanded beyond D1. A holder of an earlier password who can also write login-Keychain items can reopen an earlier file whether they plant it as the current or the pending item (characterised by `PendingPasswordGrantsNothingBeyondTheCurrentItem`, not claimed as protected).

**Qualification harness finding (necessary to obtain trustworthy evidence, not a development objective).** The first mutation attempts triggered macOS Keychain prompts that required a person to cancel. Causes: `foreignAttempt` re-enabled user interaction when it finished, undoing the process-wide setting for later tests; fixed service names let a later test binary meet items an earlier binary created; and one existing test ran `/usr/bin/security`. Fixed for qualification only: real-Keychain tests run with user interaction disabled (`DisableUserInteraction`, never called by production), use a service identity unique to the process and call, replace the external tool with an in-process removal, and may skip only when a one-time probe shows the Keychain unusable; after the probe passes any unavailability fails the test, and `PRAXIS_REQUIRE_KEYCHAIN=1` (set for qualification and mutation) turns even a failed probe into a failure. Production Keychain interaction is unchanged.

**Evidence.** Focused and full suites, `make test-current`, race, Python and vet pass (§10); the 256-subset powerset and 4096-store mixed-snapshot enumerations pass in full; **all eight preserved review-probe outcome sets are identical to the recorded ones and the Review 3 process-image A/B drive (14 scenarios) is identical to Repair 5's after normalisation** (§8); Review #6's N16 probe run unchanged now fails at its attack step (`opaque replay not reproduced`, status -25293, corrupt); the mutation inventory is regenerated from the final source (§7: 304 mutations, 274 killed, 30 classified, 0 unexplained); core, plugin and package rebuilt with a fresh build cache are byte-identical (§12).

## Repair 5 in one page

Review #5 established that **authenticity is not currency and a missing record is not proof of never having existed**. N14: after an authentic revocation, deleting the revocation row and re-inserting a byte-exact copy of the earlier sealed liveness row (no key) restored the decision across restart and a fresh controller minted a new sealed, effective completion (`AllUnitsComplete=true`). **Follow-up directive (Keychain access-control hardening).** After the first Repair 5 qualification Thomas directed that the Keychain item be hardened so unauthorized mutation is not silently permitted merely because it fails closed, without weakening the governed re-anchor or creating another recovery or authority path. The item's own access list turned out not to protect modification or deletion; a locked, password-protected dedicated Keychain does protect read, overwrite and add (design §7.1, `probes/acl-hardening/`). Everything invalidated was re-run on the modified source; the pre-hardening qualification logs, mutation inventory and report are preserved under `repair-5-evidence/qualification/superseded-pre-acl-hardening/`, and the candidate identities in §12 are the post-hardening ones.

**The architecture question and its resolution.** Repair 5 first ended in `AUTHORITY_CONFLICT` (preserved unchanged: `repair-5-evidence/AUTHORITY_CONFLICT.md`): N14 and the full-closure case of N15 are a consistent earlier state of the SQLite file, and no predicate that reads only that file can refuse a consistent earlier state (executed boundary probes; the 256-subset experiment). Thomas resolved it with **D1**: rollback and prefix-truncation of the governance store are inside the defended adversary; a minimal **Forward Authority Anchor (FAA)** outside the store is authorised as a platform-neutral contract with the **macOS Keychain as the first backend**; no network service, GitHub witness, remote ledger, TPM or other trust infrastructure. This repair implements exactly that and nothing more.

| | |
|---|---|
| Mechanism | The store keeps a hash-chained sequence of authenticated governance **facts** (a random-nonce genesis; decision, generation and supersession retirements; a Goal's entry into the governed safety domain; governed re-anchors). The FAA holds only `(sequence, head)` of that chain. Governance state is consumable only when the verified chain ends exactly at the anchor. A store that is behind, ahead of, unrelated to, or cannot be compared with the anchor yields **no governance at all**, never an older governance. |
| Atomicity | The anchor is advanced inside the store's write transaction and before the commit; retirements are written ahead of their effects. Every crash interleaving leaves a consistent state or a fail-closed stranded one, never one that broadens permission (crash matrix, design §4). |

A protected request whose proposal is missing now fails closed. |
| Not claimed | The residuals in §14 and design §7: the Keychain anchor can be **silently deleted** by another process of the same OS user (measured; the platform does not protect deletion) and can be overwritten only in the milliseconds of a genuine operation, which the store detects and refuses but which is a denial of governance; destruction plus a whole-installation wipe is indistinguishable from a new installation; a machine-level restore of Keychain and database together is a consistent earlier state of both domains. No `AUTHORITY_CONFLICT` beyond D1 was needed. |

## Repair 4 in one page

Review #4 found that a **keyless writer of the SQLite file** (no storage key, no ceremony) could widen authority with one `DELETE`: removing the `authority_revocation` row restored a revoked decision and a fresh controller minted a *new* sealed gate completion (N8); removing the `goal_safety_classification` row let a stripped plan through the supported import and a worker be dispatched with activation absent (N9). Both survive close/reopen. Repair 3's mutation inventory had explicitly *excluded* "deletion of authenticated rows by a raw writer", so its 134 kills said nothing about either.

Both are one defect: **a consequence-permitting predicate was defined by the absence of a row.** This repair states the invariant that defect violates (**I12, deletion-monotonicity**, §1), repairs the *shared boundary* instead of two rows, and reports what it does **not** defend.

| | |
|---|---|
| Mechanism | A decision or authority generation grants nothing unless its sealed **liveness** record is present. Revocation, invalidation and root succession retire (delete) that record; it is written in the same transaction as the fact it keeps alive; an identical resubmission never recreates a retired one. Goal classification is re-derived from surviving safety-bearing proposals and accepted-plan generations when its own row is missing; an unreadable row is an error. |
| Also found and repaired | N10 generation-invalidation deletion; N11 root rollback by deleting the successor and the predecessor's supersession; N12 a revoked decision eligible for ordinary re-request; N13 publication and recovery admission treating absence as "current" (§3a). |
| Covered adversary | **A1, a keyless delete-only writer:** no combination of deletions widens authority (single-row and paired sweeps over every sealed row). |
| **Not covered (documented, reproduced)** | **A2** delete **plus replay** of a previously copied sealed row (a rollback); **A3** total erasure of a Goal's governance history; the unauthenticated plaintext ledger. Closing A2/A3 needs a forward-only anchor outside the database file (for example a keychain monotonic counter): a new architectural component, deliberately not built. `repair-4-evidence/probes/residual_rollback_replay_test.go.txt` reproduces A2. |
| Unchanged | the accepted storage-key trust root; no product semantics or authority added; no `AUTHORITY_CONFLICT` was needed. |
| **Migration consequence** | Decisions and generations written before liveness records existed are **not in force** under this candidate. An installation that predates it obtains liveness through governed root succession (which now writes it atomically) and fresh decisions. Nothing is backfilled. |

## 1. Final invariants I1–I14

| | Invariant |
|---|---|
| I1 | Execution-derived state cannot be supplied as accepted intent. |
| I2 | Every safety-bearing ingress receives equivalent enforcement. |
| I3 | Historical authority is not necessarily current executable authority. |
| I4 | Missing required evidence cannot become success. |
| I5 | Evidence is exact, unambiguous, bounded, and bound to what was actually executed and published. |
| I6 | Activation verifies the runtime actually acting. |
| I7 | Authority gates never reach a provider. |
| I8 | Protected decisions require authentic ceremony lineage. |
| **I9** | **Downgrade resistance.** A governed object cannot escape stronger safety semantics by removing, omitting, weakening, relabeling or corrupting the metadata that identifies them; classification never depends solely on a self-declared field of the object being admitted. |
| **I10** | **Outward-effect equivalence.** Every externally observable or irreversible effect is guarded by the same current authority, activation, binding and evidence predicates required to admit it as governed durable consequence, established *before* the effect. A residual check-to-effect interval is bound to the exact object (the qualified commit id) or detected and recorded as ungoverned. |
| **I11** | **Authenticated completion consumption.** Execution-derived completion affects future eligibility only if its exact evidence and governing lineage are authenticated and re-validated at the point of consumption. Historical completion stays history; current eligibility is separately established. |
| **I12** | **Deletion-monotonicity.** Every predicate that permits a consequence is monotone *decreasing* in the set of governance rows: removing, corrupting or failing to read any row may leave permission unchanged or smaller, never larger. "No negative record exists" is anti-monotone and is not admissible as evidence that anything is permitted; permission requires positive, authenticated presence. |
| **I13** | **Temporal authority.** A governance fact is consumable only if the store's authenticated fact chain is exactly the chain the forward authority anchor pins outside the store. Once authority or classification has been retired, no earlier authentic state — restored whole, restored in part, or replayed row by row — can make it executable again; a store that is behind, ahead of, unrelated to, or cannot be compared with the anchor yields no governance rather than an older governance. |
| **I14** | **Subject-governance continuity.** A subject's entry into the governed safety domain is an anchored fact. Erasing, truncating or rolling back the store's evidence cannot make that subject indistinguishable from a never-governed one: either the fact survives, or the missing suffix is detected against the anchor and governance is refused until a governed re-anchor. |

I1–I8 were reconciled against the frozen v4 plan and are unchanged in meaning. I5 was tightened (bounded; bound to what was *published*, not only executed). I13 and I14 are new in Repair 5: I12 is monotone over a fixed row set and does not cover time or continuity, so it is complemented, not replaced (I12's statement is unchanged; its implementation over the whole evidence set is completed). They compose with I3 (I13 is its temporal form), I9 (I14 makes classification survive erasure), I10 (every effect admission re-checks freshness in the admitting transaction) and I11 (a resurrected decision cannot re-legitimise a completion); none is weakened, because the FAA can only remove permission, except for the one owner-attested root re-admission of a governed re-anchor. I12 was new in Repair 4 and is a strengthening common to I3, I9, I10 and I11 (I3 says a revoked fact must not be current but not how "revoked" is known; I9 says classification may not depend on a self-declared field but not that it may not depend on one row's survival; I10 and I11 inherit both because the decision they re-validate could be resurrected). It changes no frozen v4 semantics and adds no authority: the liveness record is the implementation of the existing predicate "this decision or generation is current authority". I9–I11 are new in Repair 3; each derives from a Review #3 finding and none changes frozen v4 semantics: I9 enforces plan §2.2's rule that a plan enters only through the authority-backed path; I10 and I11 enforce §3/§4's fail-closed completion and gate semantics. No invariant strengthens the ceremony trust model beyond frozen plan §9 ("V4 does not claim stronger cryptographic human authentication than current Praxis provides").

## 3. N1–N7 corrections

**N1 — safety downgrade (I9, P1).** Every fence used to key on `WorkPlan.Safety != nil`, a field inside the plan bytes that `Save`/Import accept. Now: (a) the first safety-bearing proposal for a Goal writes an authenticated, immutable classification record before the proposal is persisted (attachment re-marks idempotently); (b) `Save`/Import/Finalize/establish refuse *any* WorkPlan for a classified Goal; (c) proposal, review, legacy acceptance, the authority-backed acceptance bridge and attachment each refuse a binding-less artifact for a classified Goal, and a binding for another kernel version; (d) the Goal-drive controller, runtime admission fence and materialization treat a classified Goal whose generation lacks the binding as `ErrSafetyDowngrade` **before** any admission or worker (a store fault is never "legacy": it fails closed); (e) content guard: a plan with kinds, preserved specification bytes or gate provenance but no binding is refused at proposal and accepted-plan validation, each tell on its own; (f) attachment binds the accepted plan to the Goal it was accepted for (Astra R1-G). Genuinely unclassified legacy Goals are untouched (control tests). A plan-less successor of a classified Goal may be persisted (it is not a plan) but cannot be driven.

**N2 — completion authentication (I11, I3, P1).** A ledger row is now evidence only if (1) it is structurally the evidence its kind requires, (2) its exact bytes carry a seal authenticated under the installation storage key (written by the controller after qualification, before the ledger append; keyed by the completion digest and scoped to the Goal generation), and (3) for a gate, the request its dossier implies, the recorded request, the decision, the dossier and the owner-ceremony record are re-resolved from authenticated state at every consumption. An unresolvable citation is an error (forgery/corruption). An authentic decision that is no longer effective (revoked, rejected, expired) **demotes** the completion — and every unit that hard-depends on it — to *historical*: it stays in the ledger and stays readable, but authorizes nothing. Consumption sites: selection (both branches of `prepare`), Goal candidate derivation, structural assessment, lifecycle status (`inspect` reports why and is not drivable when a completion cannot be authenticated), and the explicit/recovered objective, which must also be currently *runnable* (Astra R2-F5).

**N3 — Darwin process-image identity (I6, P2).** Verified empirically on this machine (darwin/arm64, go1.27.1, no cgo): the kernel's exec-time code-directory hash (`csops CS_OPS_CDHASH`) of the process stays the *original* value after an in-place overwrite, a truncate-and-write, and an atomic rename (`3b5f3690…b8857`, flags `0x22020201`, process unharmed and still running A). Verification now requires the kernel value to equal the hash of a CodeDirectory embedded in the file bytes read through the retained descriptor, every code page of those bytes to re-hash to that CodeDirectory's page hashes, the code limit to end exactly at the embedded signature, `CS_VALID` to be set, and the file's full SHA-256 to equal the manifest digest. This closes the in-place overwrite **and** the replacement between kernel exec and package initialization, which a hash-once fallback could not have closed. Fail-closed: unsigned executables, universal binaries, scatter signing, malformed signatures, `csops` failure. Uncovered: bytes after the signed code (only the manifest digest covers the signature container). Non-darwin: no kernel identity is consulted; the claim rests on the OS refusing writes to a running executable (Linux `ETXTBSY`), from code and documentation only; Windows is unqualified; darwin/amd64 compiles and fails closed for unsigned builds. The mechanism uses `syscall.Syscall6` (deprecated but present); if a future macOS or Go removes it, verification fails closed. `go.mod` is unchanged.

**N4 — semantic duplicate keys (I5, P2).** `UnmarshalExactJSON` walks the tokens against the destination type: keys resolve to fields by exact JSON name, a key that matches only by case folding (ASCII, Kelvin sign, long s) is refused, textual duplicates are refused at every depth, invalid UTF-8 and unpaired surrogate escapes are refused, input is bounded (1 MiB), nesting is bounded (64), exactly one value is accepted, and unknown fields are refused where requested. A 400-case differential test checks that random case-mutations are refused exactly when `encoding/json` would have accepted them. Wired into: dossiers, gate contracts, governed-output contracts, candidate/relationship specifications, activation manifest, ceremony and classification records, **the baseline import document, all six lifecycle request bodies, the evaluation document, the worker result, and the baseline load**. Not wired, by design (see §13): plaintext ledger payloads (the seal is the control) and store-authenticated proposal/acceptance/request/decision records (authenticated ciphertext; the 1 MiB cap is a risk for those larger records). A dead second duplicate check was removed rather than left as a guard that cannot fire.

**N5 — index hints and byte identity (I5, I10, P2).** Validation no longer runs in the worker checkout. `RunBoundValidation` exports the exact checkpoint commit into a private directory (a fresh clone that copies objects but not hooks, config, excludes, index or hints; hooks, fsmonitor, replace refs and global/system config are disabled), runs the validator there, then proves the export is still the checkpoint by HEAD, tree, hint-flag scan, status, untracked/excluded scan **and** a content re-hash into a fresh index, and re-proves the worker checkout's HEAD/branch/validator binding. Publication pushes the exact object id (not `HEAD`) and verifies the remote ref afterwards. Tests cover assume-unchanged, skip-worktree, staged/unstaged drift, index/worktree disagreement, `.git/info/exclude`, fsmonitor and hooks, tree/checkpoint substitution, a status-blind same-size rewrite that only the content re-hash can see, a validator that reaches back and moves the worker checkout, a HEAD-moving export, non-object-id checkpoints, a remote that ends elsewhere, replace refs, and clean legitimate publication. Behaviour change: a validator that relied on untracked or ignored files of the worker checkout no longer sees them.

**N6 — output bound (I4, I5, P2).** The collector no longer embeds `bytes.Buffer` (whose promoted `ReadFrom` bypassed the bound). The 1 MiB budget is shared by stdout+stderr; overflow cancels the process group and the run fails closed **whatever the exit status**; the tree is terminated after the validator returns. **N7 — Goal completion candidate (I11, new in this repair).** Found by the equivalent-path search: the candidate an owner is shown as "controller-verified" before settlement is a plaintext ledger record embedding unit completions. Both `--operation=evaluate` and `--operation=complete` now refuse a candidate that is not exactly the authenticated, currently effective set.

**Surviving post-worker mutations (I10, I1).** Each of the five was reproduced against the Review #3 candidate (M2b settle-time authority, M2c pre-gate-completion, M2d settle-time activation, M6b settle-time binding, M12 claim of a non-selected unit) and now has a regression that turns red when its guard is removed (§7): a drifting verifier per boundary proves that on failure *before* publication nothing is pushed and no completion is recorded, and that on failure *after* publication the turn is durably recorded `BLOCKED`, `CheckpointPublished:true`, `UnitCompleted:false` ("published but governed completion was refused"). A lost lease records nothing, as before. ## 3a. N8–N13 corrections (Repair 4)

**N8 — deleting a revocation restores authority (I3, I10, I11, P1).** `LoadAuthorityDecision` treated "no `authority_revocation` row" as "in force". Now a decision grants only while its sealed liveness record (`authority_decision_live`) is present and names the exact decision digest. `SaveAuthorityRevocation` deletes that record *before* writing the revocation (a crash between leaves the decision not live, the fail-closed direction; a retry completes it). The liveness record is written in the **same transaction** as the decision (and, for delegated decision+generation, in the same transaction as both), so no replay is ever needed to create it, and an identical resubmission of a stored decision *requires* the record instead of recreating it (`ErrAuthorityDecisionNotLive`, which is also an `ErrAuthorityDecisionRevoked`, so every caller that refuses a revoked decision refuses it). Preserved probe: after the keyless `DELETE` the decision is refused and no new completion is minted; regression `TestRepair4N8RevocationRowDeletionDoesNotRestoreAuthority`, plus store-level `TestRevocationRowDeletionDoesNotRestoreAUnprotectedDecision`.

**N9 — deleting the classification removes the downgrade fence (I9, P1).** `GoalSafetyKernel` treated "no `goal_safety_classification` row" as "legacy Goal". Classification is now the sealed row **or**, when it is missing, derived from every surviving safety-bearing artifact of the Goal (proposals and accepted-plan generations; attributed by Goal identity, conflicting kernel versions refused, an undecryptable or mismatched candidate row is an *error*, never "unclassified"). A classification can only *add* governance, so it cannot be made monotone by one positive row; deriving it from at least two independent surviving artifacts means no single deletion removes it (`TestRepair4SweepSingleRowDeletionNeverUnclassifiesGoal`, `TestRepair4SweepClassificationRowPlusAnyOtherRowStillClassified`). Total erasure of every artifact of the Goal is residual A3. Preserved probe: the stripped import is refused; regression `TestRepair4N9ClassificationRowDeletionStillRefusesStrippedImport`.

**N10 — deleting a generation's invalidation restores it (I3, I12; found by equivalent-path search).** `ValidateAuthorityGeneration`, the lineage walk, the in-transaction fences of both `PutSecureBlobUnlessRevoked` and `PutSecureBlobsUnlessRevoked`, and the lifecycle repair guard's `IsSecureBlobRevokedInTx` all read "no invalidation row" as "live". They now share one in-transaction predicate (revoked **or not live**) and one goalstore predicate (`requireLive`); a generation is live only while its sealed `authority_generation_live` record is present, retired by invalidation or supersession.

**N11 — root rollback by deletion (I3, I12).** `loadInstallationRoot` accepted "exactly one root without an invalidation". Deleting the successor's generation row and the predecessor's supersession record left the superseded predecessor as the sole "active" root. The liveness records are now read **in the same snapshot statement as the generations** (reading them separately reintroduced the very race that snapshot exists to prevent: a concurrent succession produced spurious "installation root ... liveness record is missing" errors in 18 of 60 fan-out runs before this was fixed), a current-form root must be positively live, and `PutRootAuthoritySuccessor` retires the predecessor and admits the successor in the transaction that supersedes it. The pre-delegation root read under a source-schema migration view predates liveness records and is verified against its own bytes, unchanged.

**N12 — revoked decision eligible for ordinary re-request (I3, I12).** `verifyHistoricalReRequestPredecessor` refused a *revoked* decision only if the revocation row existed; deleting it made a revoked decision look merely expired. The predecessor decision must now still have its liveness record.

**N13 — publication and recovery admission read absence as "current" (I10, I12).** `CheckGoalsPublicationInvalidation` and the in-transaction `RevalidateGoalsPublicationRecoveryAuthorizationTx` required only that no revocation/invalidation row exist. Both now also require the decision's and every generation's liveness record.

Every one of N10–N13 has a regression that fails when its guard is removed (mutations `R4.*`, §7). None was replayed against the Repair 3 binary; the evidence that each was a real hole is that the regression turns red when only the Repair 4 guard is disabled. Regressions are keyless SQL deletions with no `Crypto` or `KeyRef` involved (`cmd/praxis/bootstrap_v4_repair4_test.go`, `internal/goalstore/liveness_test.go`, `internal/state/liveness_test.go`); the sweeps delete every sealed row of the gate fixture singly (and, for classification, in pairs with the classification row) and every sweepable non-sealed row (schema-bookkeeping rows make the installation refuse to open, which fails closed; a few are protected by foreign keys and refuse the delete).

**Existing fixtures.** Test fixtures that wrote decisions or generations through the low-level store now write liveness records the way production code does (`MarkLive` on `PutAuthorityGeneration`; `SealedLivenessRecord` for the fixture decisions in `internal/goalspublication` and `authority_rerequest_test`). No assertion was weakened.

## 3b. N14 and N15 corrections (Repair 5)

**N14 — authentic stale state restores authority (I3, I10, I11, I13).** After an authentic revocation, delete the revocation row and re-insert a copied sealed liveness row; restart: the Repair 4 store accepted the decision and a fresh controller minted a new effective completion. Now the revocation is an **anchored fact** written ahead of its effects; the liveness row and the revocation row are derived. The replayed row is authentic and irrelevant: the decision is retired by a fact the adversary can neither delete (the chain would break against the anchor) nor forge (sealed). Whole-database rollback, mutually consistent subsets, prefix truncation and a chain with a gap are all refused for the same reason. Regressions: `TestRepair5N14ReplayedLivenessDoesNotMintACompletionAfterRestart` (production constructors, real controller), `TestFAAReplayOfACopiedLivenessRowDoesNotRestoreARevokedDecision`, `TestFAAWholeDatabaseRollbackFailsClosed`, `TestFAAFactChainTruncationErasureAndDamageFailClosed`, `TestFAAMixedSnapshotAdversaryNeverRegainsRetiredAuthority` (4096 mixed stores).

**N15 — selective erasure produces legacy permission (I9, I10, I14).** Repair 4 derived classification from three of eight evidence kinds and read "no source" as legacy. Now (a) classification is an anchored fact written before the classification row and before the proposal, and it survives every deletion of every evidence row (`TestRepair5EvidencePowersetClassificationQualification`, `TestFAAClassificationSurvivesErasureOfEveryEvidenceRow`); (b) the in-store fallback consumes a registry of every kind of record that evidences governance (baseline generations, proposals, reviews, acceptances, protected requests, decisions, completion seals), and `TestGoalEvidenceRegistryCoversEveryGovernanceNamespace` fails on any namespace that is neither evidence nor declared non-evidence; (c) a protected request whose referenced proposal is missing fails closed instead of skipping the activation check. Regression: `TestRepair5N15ErasingClassificationSourcesDoesNotDowngrade`.

**Semantic coverage boundary (stated, not a claim of exhaustiveness).** The 256-subset powerset is exhaustive over the eight Goal-attributable evidence rows of the gate fixture: the Repair 4 classifier is fooled by 32; the in-store derivation alone by exactly one (deleting all eight, an honest pre-governance state that only the anchor can distinguish); the anchored classifier by none. The 4096-store enumeration is exhaustive over six row groups times four honest states. Neither is a powerset over the whole database (2^30 and beyond); rows outside those groups cannot change the answers they check. Rollback resistance is otherwise argued and tested by explicit state-transition tests, not claimed from mutation.

**Crash and atomicity analysis.** SQLite and the Keychain cannot share a transaction. Design §4 tabulates each interleaving (anchor write fails, backend lies, crash after the anchor advanced, commit failure, crash after the fact, root succession interruption, interrupted initialisation, interrupted re-anchor) with the state left and the verdict; each is a test. The rejected alternative (commit, then advance) would let a crash leave a store that lost a retirement the anchor never learned of.

**Backup restore and re-anchor.** Design §5. Legitimate restoration of an older database is refused like any rollback; the governed ceremony is the only recovery, it is durable and inspectable, and it never makes retired authority current (`TestFAAGovernedReanchorAfterRestoreDoesNotResurrectRetiredAuthority`, `TestRepair5WholeDatabaseRollbackIsRefusedAndRecoveredOnlyByTheGovernedCeremony`). Authority for it is derived from the installation owner's existing ceremony (interactive terminal, the OS user recorded in the root's enrolment provenance, digest-bound typed confirmation); no new authority was invented.

## 3c. Keychain access-control hardening (follow-up directive)

**Directive.** After the first Repair 5 qualification Thomas directed: harden the Keychain item's access control; unauthorized mutation must not be silently permitted merely because the resulting state fails closed; preserve the existing fail-closed behaviour; prevent unauthorized silent overwrite where the platform permits; do not weaken the governed re-anchor or create an alternate recovery or authority path. The deletion behaviour and the narrowed unlocked-operation window below are **measured residuals for independent review**, not further repair triggers.

**Final architecture** (`internal/crypto/faa_keychain_darwin.go`; design `repair-5-evidence/design/forward-authority-anchor.md` section 7.1). The anchor state lives in a **dedicated, password-protected Keychain file per installation** (`~/Library/Keychains/praxis-faa-<hash>.keychain-db`). Its password is **32 random bytes generated by Praxis**: never the user's login password, never typed, never displayed. The password is held in a **separate login-Keychain item** whose access list trusts only the code identity that created it. The file is **locked except for the milliseconds of one operation**, re-locked before every return, and configured to lock itself after five seconds so that a crashed process cannot leave it open. An in-process mutex and an advisory file lock serialise sessions. Reading the anchor needs the password item; updating or adding needs the password. Failure classification keeps the governed re-anchor the only way back: a missing keychain file is a **missing** anchor; a missing, replaced or malformed password item, or a file that cannot be unlocked with it, is a **corrupt** (unreadable) anchor, which the ceremony's existing `unreadable` path repairs by tearing down the pair and creating a fresh one holding the new anchor value; environment failures (no access, cancelled prompt, framework error) stay **unavailable** and the ceremony refuses them. Nothing here grants authority, adds a recovery route, or changes what a re-anchor admits (`TestFAAKeychainPasswordLossFailsClosedAndTheGovernedReanchorRecovers` runs the ceremony against the real Keychain).

**Properties demonstrated by measurement** (`repair-5-evidence/probes/acl-hardening/`; the attacker in each case is a differently linked binary of the same OS user without the password, with user interaction disabled so that a refusal returns a status instead of putting a dialog on the screen):

| Attempt against the real hardened anchor | Result |
|---|---|
| read the anchor | refused (`-25293` / `-128`) |
| overwrite the anchor | refused (`-25293` / `-128`) |
| add another item to the anchor's keychain | refused (`-25293`) |
| delete the anchor item | **succeeds silently** (status 0); the anchor then reads as **missing** and governance fails closed |
| the anchor after the refused attempts | unchanged and readable by Praxis |

**Approaches tested that did not provide the expected property** (kept as evidence, `item-acl-and-dp-keychain-measurement.log`, `aclprobe_main.go.txt`):

* **Restricting the item's own access list.** The item was created with every modification-related access entry (encrypt, integrity, decrypt and the rest) restricted to the creating binary. Another process of the same user (`/usr/bin/security`) still **overwrote and deleted it silently**. The list protects reading only. Altering the list afterwards needs the Keychain password (`-25293`).
* **Data-protection Keychain and `SecAccessControl` flags.** Unavailable to an ad-hoc-signed command-line tool: `-34018` (missing entitlement). Using them would need a signed application identity and provisioning profile, which is trust infrastructure D1 did not authorise.
* **An unlocked dedicated keychain.** While the file is unlocked for a genuine operation another process can overwrite an item in it (measured); hence the lock discipline above.
* Process note: a first attacker probe used the `security` tool against a throwaway locked keychain and put password dialogs on the user's screen (the password was a random value the probe had chosen, not the user's). The qualified probes use the interaction-disabled helper. No production or user Keychain item was touched by those probes; only test-named items and files in temporary directories.

**Residuals (measured; all fail closed; none can forge a valid anchor state because the value is `(sequence, head)` and the head is not computable):**

* **Deletion is a fail-closed availability residual.** The platform does not protect deletion of a Keychain item, of the keychain file, or of the password item; any process of the same user can do it silently. The anchor then reads as missing or corrupt, governance refuses, and only the governed re-anchor recovers (a denial of governance, not a forged authority). Deleting the anchor together with emptying the store is the whole-installation wipe of R-K1.
* **Bounded unlocked-operation race window.** During the milliseconds a genuine operation holds the file unlocked, another process could overwrite an item in it (measured). The result would be a value that fails validation, i.e. a corrupt anchor, which fails closed; it cannot become a chosen earlier valid state. The window is narrowed (previously one command could overwrite the anchor at any time), not closed.
* **Upgrade prompt behaviour.** The anchor's items trust the exact binary that created them, and an ad-hoc-signed Go binary changes identity with every build. After a core replacement the first use by the new binary raises the standard macOS "allow access" prompt for the password item (and the anchor item), exactly as the installation storage-key item already does; the login Keychain password entered there is the platform's, and the dedicated keychain's own password is never asked for. In a non-interactive session the read fails as **unavailable** (fail closed) until approved. The installed core is unchanged by this repair, so this applies at the future installation, which the hard boundaries keep out of scope here.
* **Read protection is per binary identity; the user's login Keychain password unlocks the password item on approval.** A holder of the storage key or an approved Keychain accessor remains the accepted trust root (R-K3); a restore of the login Keychain file together with the dedicated file and the database remains R-K2 (restated by Repair 6).
* **Platforms without a backend** (non-darwin) have no anchor and governed operations fail closed.

**Test and mutation coverage.** New regressions, all against the real Keychain in temporary directories with test-named items: refusal of overwrite, add and read without the password; silent deletion reads as missing and only the ceremony recovers; damage to the password item (removed, replaced, malformed) reads as corrupt and the reset recovers; a removed keychain file reads as missing and a read never creates one; an unpopulated new keychain is removed; concurrent sessions are serialised and cleanup leaves nothing behind; and the end-to-end ceremony test above. Mutation: the five earlier Keychain guards (R5.70-R5.74) were re-expressed against the rewritten code, and **eight new guards and two joint mutations** were added (R5.77-R5.84, R5.79j, R5.82j): re-locking after every session, password-item loss and malformation classification, unlock-failure classification, reset teardown, read never creates, unpopulated-keychain cleanup, missing-file classification. Results: R5.70-R5.72, R5.74, R5.77, R5.78, R5.80, R5.81, R5.83 and both joint mutations are **killed**; R5.79 and R5.82 first survived as masked redundant layers and are classified with their killed joint mutations; R5.84 (a stat error other than not-exist) is redundant by construction because the lock file in the same directory fails first; R5.73 (read-back verification against a backend that lies) remains unmodeled on the real Keychain and is killed on the test double. **Documented untested timing behaviours:** the five-second self-lock setting (it exists to bound a crashed process and cannot be exercised without one) and the cross-process advisory file lock (tests exercise only the in-process mutex). Neither is claimed as tested.

## 6. Ceremony trust statement (unchanged disposition, made precise)

Astra's disposition stands: **ACCEPTABLE_BOOTSTRAP_TRUST_ASSUMPTION**. No HSM, out-of-process attestation or hardware confirmation was added.

- **What possession of the installation storage key (or a `Repository` handle carrying it) permits:** writing any authenticated record — a syntactically valid `OwnerCeremonyEvidence` for the enrolled OS user, an `AuthorityDecision`, roots, requests, the **Goal classification record**, and **completion seals**. The R1-F probe still shows a gate approved with no TTY. This is the frozen v4 trust root: the OS-user/keychain-held key plus the interactive TTY check (which accepts any character device).
- **What write access to the SQLite file *without* the key permits (revised in Repair 5).** Appending plaintext ledger and activity events (refused at every consumption for lack of a seal); deleting rows (Repair 4: nothing widens); **copying, restoring, replaying and truncating** (Repair 5: refused, because governance state is consumable only when its fact chain ends exactly at the forward authority anchor, which such a writer cannot reach). What such a writer can still do is **deny** governance by making the store inconsistent with the anchor, which is refused and recovered only by the governed ceremony.
- **What the Keychain anchor does and does not provide (measured).** A SQLite-file writer cannot reach it. The first Repair 5 design (one login-Keychain item) could be **silently overwritten and deleted** by another process of the same OS user, and restricting the item's own access list did not prevent that; Thomas directed that this be hardened where the platform permits. **Hardened design:** the anchor lives in a **dedicated per-installation Keychain file, locked except for the milliseconds of one operation**, protected by a **random 32-byte password that Praxis generates** (never the user's login password) and holds in a separate login-Keychain item that trusts only the creating binary. A differently signed process without the password, with interaction disabled, is now **refused on read, overwrite and add** (measured against the real implementation, `probes/acl-hardening/`). **Not preventable on this platform:** silent deletion of the item, file or password item (fail-closed as missing or corrupt, recovered only by the governed ceremony), and an overwrite inside the unlocked window of a genuine operation (fails validation, so also fail-closed). That adversary cannot set the anchor to a chosen earlier *valid* value, because that needs `(sequence, head)` and the head is inside sealed rows and unreadable without the key or an approved read (the genesis carries a random nonce so even the empty chain is not computable). The data-protection Keychain and access-control flags are unavailable to an ad-hoc-signed CLI (`-34018`). Consequence: after a core replacement the first use by the new binary raises the standard macOS access prompt, as the storage-key item already does. Residuals R-K1 to R-K3 are in §14; nothing in the frozen architecture protects a holder of the storage key or an approved Keychain accessor, which is the unchanged accepted trust root.
- **Consequence for N2:** the completion consumption boundary is exactly as strong as the accepted trust root and no weaker; Review #3's finding that the ledger was a *weaker*, key-less boundary is closed.

## 14. Unresolved blockers and residual limits

0. **A fresh, complete independent review (Astra Review #7) is required.** Six reviews each found defects only after crossing component boundaries; Repairs 3, 4 and 5 also found N7, N10–N13 and the command-level anchoring gap by inventory. Unreviewed surface may remain.
1. **Storage-key holder** can still forge any authenticated record, including the classification record, completion seals and liveness records (accepted bootstrap trust root, §6).
2. **The store's adversary (revised in Repair 5).** Delete, replay, restore, truncation and erasure of the SQLite file are refused (I13, I14). Bounded residuals, none hidden: **R-K1** the Keychain anchor can be silently DELETED by another process of the same OS user (measured; the platform offers no protection against deletion), and overwritten only during the unlocked window of a genuine operation: the store is refused and only the governed ceremony recovers it, which is a denial of governance, and destruction combined with a whole-installation wipe is indistinguishable from a new installation; **R-K2** (restated by Repair 6 after Review #6 finding N16) the dedicated Keychain file is re-keyed on every anchor advance, so an opaque copy of that file no longer opens with the current login-Keychain password item; what remains is a same-user process that also restores an earlier copy of the LOGIN Keychain file (which holds the password item) together with the dedicated file and the database, i.e. a consistent earlier state of all three domains, which no file-based Keychain backend can distinguish; **R-K3** a holder of the storage key or an approved Keychain accessor can forge anything (accepted bootstrap trust root). The access-control hardening Thomas directed is implemented as far as the platform allows (locked dedicated Keychain, §7 and design §7.1); it ties access to the Praxis binary identity, so the first use after a core replacement raises the standard macOS access prompt, and in a non-interactive session fails closed as unavailable. The five-second self-lock and the cross-process advisory lock are not exercised by tests.
